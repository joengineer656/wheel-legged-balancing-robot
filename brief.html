The wheel-legged
balancing robot

wheels that balance, legs that change the game — one robot, three controllers, one honest experiment.

A balancing robot is an inverted pendulum: unstable at every instant, upright only because a controller reacts faster than a human can. This project builds that robot — each wheel on an adjustable leg — and uses it to answer a question bigger than the machine itself: does model-based control actually pay off on real hardware? PID, LQR and MPC run on the same robot, the same model, the same tests. Only the mathematics changes.

03 System architecture

Two layers, strictly separated. The fast layer only ever sees the state estimate; the slow layer only ever issues targets. This is the single rule the whole design protects.

layer 1 — realtime balance · MCU · 200–500 Hz layer 2 — perception · SBC · ROS 2 · added in stage 3
*model confirmed during V0 bring-up — pins in config. if layer 2 dies, layer 1 keeps balancing or shuts down safely
No perception in the balance pathSLAM, vision and navigation can crash, lag or vanish — the loop never notices.
The MCU has the final wordevery command from above is validated and clamped against hard limits.
Heartbeat or nothing60 ms without the computer's heartbeat and the motors are cut — no questions.

05 How the comparison stays honest

A comparison is only worth a thesis if the rules are fixed before the first run. These are the rules.

Fairness rules

  • Same robot, same sensors, same battery, same motor driver.
  • Same model — identical A and B matrices.
  • Same state estimation for all three.
  • Same Q and R weights at first; only the solver differs.
  • Same control rate, or the difference is documented.
  • Same tuning effort: equal sessions, separate tuning / eval sets.
  • Every final parameter written down before evaluation.

06 Roadmap — nothing advances past its gate

  1. nowV0 — PID baseline, two wheels

    Small frame, ESP32, N20 motors + DRV8833, MPU-class IMU. Complementary filter, estimator, safety module, telemetry from day one. MATLAB cart-pole tuned before touching hardware.

    gate30 s unassisted balance, run 10× and logged

  2. stage 1LQR on the same frame

    State-space model from real parameters, gains from Q and R. Gain scheduling for leg height arrives with stage 2.

    gatebeats or matches PID on identical tests

  3. stage 2MPC with explicit constraints

    Horizon, limits, QP solver. Given engineering priority over scope creep: the MCU was chosen with QP-in-5-ms in mind.

    gatesolver fits the cycle, headlessly measured in sim first

  4. stage 3Legs + perception

    Height-only legs first, gain-scheduled per height. Then SBC, LiDAR, camera: obstacle avoidance, mapping, following. Legs never use uncontrollable hobby servos.

    gatebalance layer untouched — perception is a bolt-on

  5. stage 4Thesis

    Model, derivation, three controllers, tables like the one above, an honest analysis — written in parallel from V0, not at the end.

    gatea valid comparison — even if MPC does not win

08 Non-negotiable safety

  • |θ| > 30°motors cut immediately — the robot may fall, the lab may keep its fingers.
  • no heartbeatSBC silent for one watchdog window → motional arrest, safe state.
  • big red switche-stop always in reach; fuse on the motor rail, always.
  • tethered launchesevery new controller, better or worse, runs first on the leash.
