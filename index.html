Al-Balqa' Applied University · graduation project · mechatronics engineering — short summary

Wheel-legged
balancing robot

PID vs LQR vs MPC — same robot, same model, same tests.

A balancing robot is an inverted pendulum: unstable at every instant, upright only because a controller reacts faster than a human can. This project builds that robot — two wheels, an adjustable leg on each — and uses it to answer a question bigger than the machine: does model-based control actually pay off on real hardware? Three controllers run on identical hardware, an identical model and identical test protocols. Only the mathematics changes.

01 The idea in one sentence

Change only the math, keep everything else identical — then any difference in performance belongs to the algorithm itself, not to the hardware, tuning, or test conditions. That's the scientific method applied to control.

Most control papers prove that a controller works. Fewer prove that one controller is better than another, and fewer still do it fairly — on one robot, under one protocol, with the tuning effort counted. The fairness rules are fixed before the first run, so the result is a measurement rather than a demo.

03 Why LQR and MPC — and why compare them

They're siblings: both are model-based optimal controllers that minimize the same quadratic cost (same Q, R). The difference is the constraint handling.

LQR

the cheap, classical answer
horizon
infinite — solved offline
constraints
ignores them
compute
one matrix multiply: u = −Kx

One gain matrix, evaluated every cycle. Nothing to solve at runtime.

MPC

the expensive one
horizon
short window — solved every cycle
constraints
torque / tilt limits built in
compute
an optimisation problem, ~500× per second

Plans ahead over a finite horizon, then executes only the first move and plans again.

So the real question is: when do constraints matter enough to justify solving an optimisation 500 times per second? This project measures where the crossover is.

04 What everyone else does — and the gap

  • 01
    One controller, and stop. Most papers implement a single controller — usually PID or LQR — show that it balances, and make no comparison at all.
  • 02
    Unfair comparisons. When comparisons happen they're usually different robots, or simulation-only, or unequal tuning effort. This is extremely common.
  • 03
    The gap. Same-robot, same-conditions, real-hardware comparisons are rare — that's exactly the gap this project fills, and why the fairness rules matter.
  • 04
    Same debate elsewhere. Automotive lane-keeping, drones, wheeled bipeds (Ascento runs LQR + whole-body control) — the comparison is always constraints + compute vs. simplicity + speed.

06 The expected honest result

LQR is enough for ordinary balancing. MPC measurably wins near torque limits, during pushes, and in leg-height changes — at the price of compute. If they perform the same, that's also a valid thesis finding: the crossover point is the result, whichever side it lands on.

"Both controllers get the same robot, the same model, and the same tests — I'm measuring the price of knowing your limits."

07 Roadmap

now · V0PID baseline

Two wheels, ESP32, N20 + DRV8833, IMU. Tuned in MATLAB first. Gate: 30 s unassisted, logged 10×.

stage 1LQR

Same frame, same model, gains from Q and R. Gate: matches or beats PID on identical tests.

stage 2MPC

Horizon, limits, QP solver. Gate: solver fits the cycle, measured in sim first.

stage 3Legs + perception

Height-only legs, then SBC / LiDAR / camera. Balance layer never touched.

stage 4Thesis

Written in parallel from V0 onward. Gate: a valid comparison — even if MPC does not win.
